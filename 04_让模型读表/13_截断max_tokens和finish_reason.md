# 13 截断：max_tokens 和 finish_reason

[目录](../README.md)｜先修：[提示词契约](12_提示词契约.md)｜下一章：[两种读法](14_两种读法图片直读和转录作答.md)

## 1. finish_reason 是判决书

| finish_reason | 含义 | 处理 |
|---|---|---|
| stop | 说完了 | 正常解析 |
| length | 说一半被掐了 | 截断，输出作废 |

截断的输出不能拿来投票或采纳，哪怕看起来"差不多全了"。真实批次里 4/10 的密集表结构输出全因 4096 token 用尽而作废。

## 2. 密集表必然顶爆输出预算

一张 60–95 个单元格的表，每格要 text+bbox+rowspan，结构输出 2000–4096 token 装不下。这是结构路线在真实表上的最大瓶颈。

## 3. 三条出路

1. 加大 max_tokens 到 4096 重试——只能救轻度截断。
2. 按题局部取证：只输出目标单元格和必要标签，输出量缩 10 倍。
3. 分块输出：每次只转一行，程序拼装。

比赛最终走通的是第 2 条：局部证据 + 双路核验。第 3 条在试点中未能闭合网格。

## 4. 每次解析响应先看两处

1. finish_reason 是不是 stop。
2. JSON 是不是完整闭合。

两处都过才谈解析。截断的响应原样存档，标注原因。

## 5. 练习

1. 把 max_tokens 设 200 复现一次截断，看 finish_reason。
2. 数一张 60 格表的结构输出 token 量。
3. 写一个局部取证契约：只要 3 个格子，输出量砍到多少。
